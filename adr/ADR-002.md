# ADR-002 — Interface web mínima sem framework, dados em memória

## Status
Aceita

## Contexto
O ADR-001 limitou o MVP a um núcleo de domínio testável. Para demonstrar o
fluxo completo (criar e confirmar uma doação) a quem não lê código, a equipe
precisava de uma tela. Ao mesmo tempo, a RNF01 exige que o domínio não
dependa de framework web, e o escopo da sprint não inclui banco de dados nem
autenticação.

## Decisão
Criar `app/web.py` usando apenas a biblioteca padrão do Python
(`http.server`, `html.escape`, `urllib.parse`). A interface só traduz
requisições HTTP em chamadas a `criar_doacao` e `confirmar_doacao` e
transforma `DomainError` em resposta 400 com a mensagem do domínio. A
dependência é de mão única: `web.py` importa `domain.py`, nunca o contrário.
Os dados ficam em memória (ver ADR-004) e o servidor escuta só em
`localhost:8000`.

## Alternativas consideradas
- **Flask ou FastAPI**: roteamento, formulários e testes mais simples, mas
  acrescentariam uma dependência ao `requirements.txt` e ao Docker para uma
  tela que é só de demonstração.
- **Apenas linha de comando**: sem dependências, mas não mostra o fluxo de
  forma visual na apresentação.
- **Sem interface nesta entrega**: mantém o escopo do ADR-001, mas a
  confirmação de doação ficaria visível apenas nos testes.

## Consequências
- **Positivas**: nenhuma dependência de execução nova; o `requirements.txt`
  e a imagem Docker têm só as ferramentas de teste (pytest e pytest-cov); o
  domínio segue independente (RNF01); a interface é testável com um servidor
  real em porta aleatória (`tests/test_web.py`).
- **Negativas / limitações aceitas**: roteamento e leitura de formulário
  feitos à mão; sem proteção CSRF, sem autenticação e sem HTTPS; os dados se
  perdem ao reiniciar o servidor. A interface **não** é adequada para
  produção e precisa ser substituída quando houver API HTTP e persistência.
- **Rastreabilidade**: a interface passou a ter requisitos próprios (RF06 e
  RF07, SPEC §8) e cobertura medida sem meta de 100% (RNF04).
