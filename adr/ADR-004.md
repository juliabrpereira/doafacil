# ADR-004 — Estado do servidor em atributo de classe

## Status
Aceita

## Contexto
O `http.server` cria uma instância nova de `DoaFacilHandler` a cada
requisição. Um atributo de instância seria perdido entre o `POST /criar` e o
`GET /doacoes`. A interface precisava guardar a lista de doações enquanto o
servidor estivesse rodando, sem banco de dados (ADR-002) e sem colocar
estado dentro do domínio (RNF01).

## Decisão
Guardar a lista no atributo de classe `DoaFacilHandler.doacoes`, iniciada com
uma doação de demonstração. A criação usa `type(self).doacoes.append(...)`
para deixar claro que a lista é compartilhada. O domínio continua sem
estado: recebe e devolve objetos `Doacao`.

## Alternativas consideradas
- **Variável global no módulo**: equivalente na prática, mas fica solta e
  mais difícil de reiniciar nos testes.
- **Atributo no objeto `HTTPServer`** (acessível por `self.server`): estado
  por servidor, melhor isolamento, mas exige uma subclasse de `HTTPServer`
  e mais código para uma demonstração.
- **Repositório injetado ou SQLite**: o caminho certo quando houver
  persistência, mas fora do escopo desta entrega.

## Consequências
- **Positivas**: solução de uma linha, sem dependências, suficiente para a
  demonstração local.
- **Negativas / limitações aceitas**:
  - O estado é global ao processo: todos os servidores criados no mesmo
    processo (inclusive nos testes) compartilham a mesma lista. Cada teste
    precisa reiniciar `DoaFacilHandler.doacoes`. Quando a fixture reiniciava
    um atributo com o nome errado, o estado vazou entre testes sem nenhuma
    falha visível (erro E-03).
  - Os dados se perdem ao reiniciar o servidor.
  - Não é seguro com servidor multithread. O `HTTPServer` usado atende uma
    requisição por vez, então o risco não existe hoje, mas voltaria com
    `ThreadingHTTPServer`.
- **Revisão futura**: substituir por um repositório injetado quando a sprint
  de persistência começar.
